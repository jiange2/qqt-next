# 客户端下载页：托管于 Backend-Next，微信内浮层引导外部浏览器打开

新增首个面向 C 端的页面「客户端下载页」（`/download/`，见 Backend-Next 词条）：由 Backend-Next 以静态资源托管（随镜像发布，与 admin-web 同模式），而不是独立静态文件、OSS 静态站点或 PHP 旧栈。页面只承担一件事——向用户分发 Android 安装包：应用图标、名称、「Android 版」与版本号、下载按钮。

微信内置浏览器（UA 含 `MicroMessenger`，iOS/Android/PC 微信统一判定）是首要入口场景：在其中点击下载**不发起任何下载**（微信会静默拦截 APK），改为全屏浮层引导用户从右上角菜单选择「在浏览器打开」；其余环境点击即经 `/download/apk` 下载。浮层文案不按平台分支，取覆盖 iOS/Android 的统一措辞。

版本号与安装包地址不硬编码在页面里，取自 settings 单行（`app_new_version` / `app_redirect_url`），经两个公开只读端点外露：`GET /download/app-meta` 返回 `{version}` 供页面异步渲染（取数失败仅隐藏版本号）；`GET /download/apk` 以 302（`no-store`）跳到配置地址，未配置时返回明确文案。这两者与 App 内更新链路同源——跳转地址约定为安装包直链（更新弹窗经 ACTION_VIEW 直接打开它）。发版只改后台设置，不必重发镜像。端点非 App 接口：不经遗留协议门面，不适用 ADR 0001 的签名要求。

## Considered Options

- **独立静态文件由宿主机 Nginx 直接 serve**：被拒——服务器出现仓库外的"雪花文件"，与镜像发布流程脱节。
- **页面内硬编码版本号与安装包地址**：被拒——与后台「版本更新」设置重复维护、必然漂移（该设置已被 App 更新链路消费）。
- **页面直接请求 `app_details` 取配置**：被拒——旧协议强制验签（`checkSignSalt`），把 salt / package_name 写进公网页面源码不可接受。
- **服务端模板注入版本号到 HTML**：被拒——页面不再是可独立打开的静态文件，且数据库读取失败时无回退；"静态页 + 稳定 302 端点"让核心下载动作不依赖任何前端取数。
- **覆盖其它内嵌浏览器（QQ/微博/抖音等）**：被拒——下载拦截主要发生在微信，扩大判定引入误伤面。

## Consequences

- 改页面文案/样式 = 重发 backend-next 镜像；改版本号/安装包地址 = 只改后台设置，立即生效。
- 微信引导依赖 `MicroMessenger` UA 与微信右上角菜单既有交互；微信改版需人工回归（iOS 菜单项文案为「在 Safari 中打开」，页面统一措辞为「在浏览器打开」）。
- `/download/apk` 用 302 + no-store 而非 301：地址变更立即生效，不被浏览器/中间层记住旧址。
- CDN 需为该安装包目录放行浏览器直取（空 Referer 或页面域名），否则点下载 403（沿 ADR 0006 防盗链机制配置）。
- 对外入口由宿主 Nginx 在 80 端口明文直出、不跳 HTTPS：HTTPS 页面 + 明文安装包会被 Chrome 拦截为「不安全下载」，页面与包须同为明文（沿 ADR 0004/0005 全栈明文现状）。
- 另提供全静态单文件版（`download-page-standalone.html`，由 `server/public/download/index.html` 手工派生）供外部静态托管：图标/favicon 内联为 data URI，版本号与安装包直链硬编码在页内，不发任何网络请求。为可迁移性放弃了上文的单一数据源——改版本/改地址时两个页面需手工同步，该文件仅一处待改（下载按钮 href 与版本号文案）。
- 单文件版的协议约束：HTTPS 页面下载明文 HTTP 包会被 Chrome 拦截为「不安全下载」，页面源与安装包 URL 须同协议；安装包为 HTTPS 直链时则页面可挂任意源（沿 ADR 0004/0005 全栈明文现状，当前安装包仍是明文）。
- `app_new_version` 为 Float，两位修订号（如 1.10）会截断为 1.1——与 App 端已知限制同源，后台发版时避免。
- 这是当前唯一的 C 端页面；后续新增 C 端页面时，本模式的托管位置与只读端点形态可作参照。
