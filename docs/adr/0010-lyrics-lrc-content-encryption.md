# 歌词文件内容上传即加密，App 持共享口令解密

lrc 文件在 OSS/CDN 上公共可读（ADR 0006 对 `lrc/` 允许空 Referer）且全链路明文 HTTP（ADR 0005），歌词实质上公网可扒。决定：backend-next 上传侧在 lrc 内容写入 OSS 前加密为 `elrc1:<base64url(AES-256-CBC 密文)>` 文本形态（上传入口唯一汇聚于 `saveTextFile`，歌曲表单与 OSS 直传两路自动覆盖）；Android 在歌词文本进入解析器前按 `elrc1:` 前缀判定，有前缀则解密、无前缀按明文处理（存量与内嵌文本天然兼容），解密失败归入现有「歌词加载失败」态。口令为单个共享字符串：服务端 env `LRC_CONTENT_SECRET`（缺失即启动失败，与 `OSS_NAME_SECRET` 同策略），App 端硬编码 `AppConfig`（与 `SIGN_KEY` 同暴露级），派生方式复刻 ADR 0008（sha256 定长化）。定位：抬高歌词抓取门槛、顺带护住明文 HTTP 上的传输内容；不追求对抗逆向。

## Considered Options

- **内嵌歌词文本（songs.lrcText）一并加密**：被拒——该通路目前基本不用，仅加密文件通路，App 端按前缀判定为将来留了口子。
- **旧 PHP 后台同步加密**：被拒——旧面板冻结待下线，其上传的歌词维持明文，App 前缀判定天然兼容。
- **per-song 密钥 / 经 song_info 协议下发密钥**：被拒——协议本身走明文 HTTP，下发即裸奔且添复杂度；共享口令与既有 `SIGN_KEY` 同级足够。
- **GCM / 二进制密文**：被拒——完整性校验对防扒无增益且引入固定 IV 复用风险；二进制会破坏 `fetchText` 与响应快照（Android 上下文 ADR 0012）两条既有文本链路。
- **存量明文 lrc 一次性迁移（同 key 覆盖回传）**：被拒——接受存量明文残留面，防护只覆盖新上传。

## Consequences

- 密钥进 APK，逆向可解——防护边界与 ADR 0006 的 Referer 防盗链同级：防直链脚本，不防决心足够的逆向者。
- 存量明文 lrc 与旧后台上传的 lrc 永久明文可拉；要清需另立一次性迁移。
- 换口令 = App 发版 + 存量密文重传；`elrc1:` 前缀为将来换算法/换钥留代际（`elrc2:`）。
- 管理面板零改动：`UploadField` 对象链接点开看到密文文本属预期，不做解密预览。
- 上线时序：服务端先上加密后，新上传歌词对未升级 App 显示为加载失败（解析不出），App 发版补齐解密——发版节奏由运营侧把握。
