# 专辑歌曲页整单加载，后端 2000 条兜底截断

`album_songs` 从「每页固定 10 条的翻页」改为**整单加载**：接口忽略 `page` 参数，一次返回专辑下全部歌曲（按维度顺序 `albumSort ASC + id DESC`），仅以服务端代码常量 **2000 条**兜底——超出时静默截断，`total_records` 仍返回真实总数（未来若需"仅展示前 2000"提示，无需再动协议）。Android 端删除触底翻页逻辑，进入专辑歌曲页一次拉全量；顺带修复点歌建队只含已加载页的缺陷——现在播放队列 = 整张专辑。策展播放列表（`playlist_songs`）等其余列表接口保持分页不动。旧 PHP 后端**冻结不跟随**：其 `album_songs` 逐行调用 `is_favourite()`（N+1 查询），单页 2000 条会把每次请求放大到 2000+ 次查询；存量老 App 继续打旧后端分页浏览，行为不变。两端同步改版符合遗留协议门面策略评审要求（backend-next CONTEXT.md）。

## Considered Options

- **保留 `page` 假分页语义（页大小改 2000）**：被拒——"不分页"就该有不分页的契约形态，保留假分页只会误导未来读者。
- **新增 `album_songs_all` 方法**：被拒——两套并行接口徒增维护面。
- **2000 上限做成管理后台配置项**：被拒——它是防失控的安全兜底而非运营参数，为它做管理 UI 是过度设计。
- **两阶段加载（先首屏后全量）**：被拒——为罕见的最坏情况引入复杂度与闪烁风险，不值。

## Consequences

- 超大专辑的最坏响应约 1.2MB（2000 × ~600B），明文 HTTP 下首屏等待拉长——绝大多数专辑几十首，与原 page=1 等待相当，接受。
- 协议变更与 App 发版绑定，回退需再发版。
- 过渡期新老 App 行为不一致（老 App 打旧 PHP 分页、新 App 整单加载），割接后 PHP 下线自然收敛。
- `smoke.ts` 无需改动（结构摘要人工比对，无条数断言）；`fetch-prod.ts` 打旧 PHP，不受影响。
