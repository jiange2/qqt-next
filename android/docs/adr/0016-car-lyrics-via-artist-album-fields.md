# 车机歌词借专辑行与作者行承载，标题永远真实

手机蓝牙连原车车机（卡罗拉）场景下，歌词到达车机的通道在协议层不存在：A2DP 只传解码后音频，MP3 文件及其 ID3 标签不过蓝牙；AVRCP 曲目文本属性为固定枚举（标题/歌手/专辑/曲号/总曲数/流派/时长）加封面，没有歌词或副标题位；Android 蓝牙栈对 MediaMetadata 的 subtitle/extras 在手机端即丢弃，原始草案（DISPLAY_SUBTITLE 逐行歌词）必然失效。QtMusic 车机屏可显示的文本只有那几个枚举位，因此决定借用其中两个：**专辑行承载当前句、作者行承载下一句**（车机行序实测为 标题→专辑→歌手；两行借用位以两个 setter 集中，可按实车表现互换），标题永远真实。逐行由 Service 侧 `CarLyricsSync` 监听播放进度（判定与歌词页同规则但加 1 秒前置量 `LEAD_MS`——实车实测蓝牙元数据推送+车机渲染存在约 1 秒滞后，提前写出补偿；位置在首行前视作第 0 行——歌词就绪即写首两句，不等开唱），行变化时经 `player.replaceMediaItem` 原地更新当前条目元数据（localConfiguration 不变，不打断播放；ExoPlayer 1.4.0 对仅元数据变化走原地更新快路径，播放器层不重备、不重开数据源），MediaSession 自动向蓝牙转发。歌词取数复用 song_info 详情链路与 LyricsCache（ADR 0014），歌曲 ID 经元数据 extras 从 ViewModel 传至 Service，歌词加载因此上移到播放层——不再依赖歌词页可见才触发。

选专辑/作者而非标题，依据三条：标题是车机最显眼的行且用户红线明确不占；qqt 的 Song 模型没有专辑字段、从不设置 albumTitle，车机专辑行原本为空，借用不挤掉任何现有信息；Media3 默认通知/锁屏只渲染标题与作者，手机端代价是通知作者位变为下一句歌词——用户于 2026-09-09 修订红线接受（原红线「作者永远真实」同日由用户主动推翻，改为「标题永远真实，作者/专辑行承载歌词」）。不设开关：车机不支持时对应行自然空白，符合「支持就显示，不支持就不显示」。切歌后新条目元数据为构建时的干净值，无需显式清空；单曲循环回到首行前视作第 0 行，重写首两句自然覆盖上一轮尾句；无歌词歌曲保持干净元数据。

## Considered Options

- **subtitle（DISPLAY_SUBTITLE）承载歌词**：协议层不过蓝牙，手机栈即丢弃。否决。
- **标题行承载歌词（QQ音乐部分实现路线）**：标题是车机第一行，污染最大，用户红线明确禁止。否决。
- **车机直装 APK / 车机侧 MediaController 读取**：MediaSession 是同设备 IPC，蓝牙链路无此协议，机制上不可能。否决。
- **先探针验证再产品化**：更稳但多一次装机插车；用户选择直接产品化，以行位映射集中为两个 setter 兜底——车机若不刷新某行，改两个 setter 换行位即可，逻辑不变。
- **借作者/专辑行（采纳）**：全链路可达（两字段均为 AVRCP 标准属性）、专辑行零挤占、手机端污染最小且已被接受。

## Consequences

- 伪切曲：1.4.0 `MediaControllerImplBase` 用 `MediaItem.equals`（含 mediaMetadata）在 Controller 侧判切曲，逐行元数据写入因此被 UI 进程误判为切曲事件（携带陈旧 reason），访问事实每句上报一条、「播完本曲」定时被误结算、进度保存与缓存可视化逐行空转。抑制在 `PlayerViewModel.onMediaItemTransition`：同 mediaId 且元数据有变判为歌词行更新，跳过上述副作用（队列位置等 UI 状态照常更新）；基线在伪切曲时同样前移，否则真实重选同曲（元数据与基线相等）会被误吞。已知接受边界：队列相邻重复同曲或重选同曲的真实切歌（脏元数据→干净元数据）会被误判为歌词行更新，少计一条访问事实且该边界定时器不暂停一次。单曲循环每轮（元数据未变）与 `#raw` 自愈（元数据被原样保留）照旧各计一条——ADR 0008「每次装载播放一条」口径不变。
- 抑制的正确性以条目有真实 mediaId 为前提：Media3 的 `DEFAULT_MEDIA_ID` 为空串，未 `setMediaId` 时所有条目同 id，判据退化为「元数据有变即跳过」，真实切歌也被一并误吞（2026-09-10 实车抓到：逐行上报止住，但恢复装载之后连自动切歌也无访问事实——定时结算与切歌存档同被静默跳过）。`buildMediaItems` 因此显式 `setMediaId(track.id)`，歌词行写入与 `#raw` 自愈经 `buildUpon` 原样保留该 id。
- 卡罗拉渲染借用行并支持曲中刷新已获实车验证（2026-09-10 用户观察歌词行随播放滚动，仅存在约 1 秒蓝牙/渲染滞后，以 `LEAD_MS` 前置量补偿，为实车校准值）；行位仍以两个 setter 集中，异常时调整即可。
- 手机端通知/锁屏的作者位将显示下一句歌词；若观感不可接受，后续可引入自定义 MediaNotification.Provider 从原始歌曲数据渲染通知（仅蓝牙链路吃占用后的元数据），成本一块独立代码。
- 作者/专辑字段从此被歌词占用：后台或客户端未来若引入真实专辑数据（或需要真实作者到达车机），必须先重做行位映射，否则二者冲突。
- 歌词加载触发点从「歌词页可见」上移到播放层，每首歌播放即取（song_info 的播放计数副作用，见 ADR 0014）；LyricsCache 会话缓存继续兜底，同一首歌每会话至多请求一次，代价不变。
- 流内 ID3 标准帧（TPE1 等）解析值会覆盖 App 静态设置的同名字段，标题/作者行在歌词写入前短暂显示的可能是文件标签值而非后台字段，属 Media3 既有行为，不在本 ADR 处理。
