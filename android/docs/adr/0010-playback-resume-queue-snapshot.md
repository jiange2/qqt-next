# 播放进度持久化为队列快照，冷启动恢复整个队列

「记住上次播放」此前只有半截实现：PlayerViewModel 每 5 秒把「分类 ID + 曲目索引 + 毫秒位置」落盘（LastPlayedStore），恢复端是 TODO 存根。接通恢复时发现按分类重建队列的方案存在结构性缺陷——播放队列实际来自八个点播入口（首页瀑布流、专辑歌曲页、收藏页、歌单详情、下载列表等），只有恰好按分类列表点播时「分类 ID + 索引」才对得上，其余场景恢复出错误队列甚至索引越界，且依赖网络、分类内容变更后会错位。故决定**持久化整个播放队列的歌曲快照（Song 列表 JSON）+ 队列索引 + 播放位置**：冷启动静默重建队列、`prepare` 不 `play`，MiniPlayer 显示上次歌曲与进度，点播放续播。切歌/暂停立即保存、5 秒轮询兜底；保存时距曲尾不足 3 秒的位置按 0 存；恢复续播不写入最近播放（守「点播过」语义）；旧 `category_id` 键废弃不迁移（恢复端从未上线，无存量数据）。恢复仅覆盖冷启动，Activity 重建的 UI 断连是独立的既有问题，不在本决策内。

## Considered Options

- **按分类重建队列（原保存方案）**：省空间，但与八个点播入口中大多数不重合，需网络、会错位，结构性缺陷无法修补。否决。
- **来源描述符重建（来源类型 + 来源 ID + 索引 + 位置）**：最省空间，但要为每个入口逐一实现重建映射，仍依赖网络且同样会错位。否决。
- **队列快照（采纳）**：与所有点播入口天然一致、离线可恢复、无索引错位；代价是百首队列约几十 KB 的整表重写，以及快照可能与后端内容漂移（下架歌曲按在线点播同路径失败，不做恢复特判）。

## Consequences

- 恢复出的队列与离开时逐首一致，包括后端此后已变更的内容；歌曲失效与在线点播走同一失败路径。
- 随机播放模式下恢复的乱序与上次会话不同：播放模式本身持久化（ADR 0008），乱序重建符合「随机播放」词条语义，不追求恢复上次的随机序列。
- 倍速与播放模式由既有持久化在连接后自动生效，恢复路径不重复处理。_（2026-09 注：倍速功能已全链路移除，本条现仅播放模式部分成立。）_
- 队列快照与「最近播放（仅存 ID）」是两种并存且意图不同的本地形态：前者是播放器运行时状态的恢复依据，后者是列表页回查后端的数据。不要互相「统一」。
