# 07: 多个音乐文件夹：添加、重叠拒绝、移除

**What to build:** 用户可以授权多个音乐文件夹，扫描结果合并成一个本地音乐库；与已有目录重叠的授权被明确拒绝；移除某个目录后其中歌曲从列表消失。

**Blocked by:** 05

**Status:** resolved

- [x] 可以添加第二个音乐文件夹，两个目录的歌曲合并展示
- [x] 重叠目录（新目录被已有目录包含，或包含已有目录）被拒绝并给出说明
- [x] 重叠授权不会被重复展示两次同一首歌
- [x] 「管理音乐文件夹」可查看已授权的根目录并移除其中一个
- [x] 移除目录后其歌曲立即从列表消失，正在播放的歌曲不受影响
- [x] 移除后重新添加同一目录，歌曲恢复展示
- [x] 根目录列表跨重启保留

## Answer

**重叠拒绝。** `data/local/LocalMusicRoot.kt` 新增 `List<LocalMusicRoot>.findOverlap(candidate)`：同一棵树、一方是另一方的祖先目录都算重叠。判定只能落在 provider 给的树根 `DocumentsContract.getTreeDocumentId` 上——同 authority 且一方是另一方的前缀，**边界必须落在 `/` 或 `:`**，于是 `primary:Music` 命中 `primary:Music/Rock`，不会命中 `primary:Music2`；`primary:` 这类整卷 id 与末尾带分隔符的 id 单列判定。documentId 不透明（第三方 provider）时 `runCatching` 兜底为「只按树 URI 去重」，判不出包含关系；即便漏判，同一首歌仍被内容指纹（ADR 0021）合成一条，不会重复展示——ADR 0019 的这条后果由指纹去重兜住，拒绝只是把它提前成显式行为。

`addRoot` 改成「先查树名（IO）→ 判重叠 → 才持久化授权」：重叠时**不调 `takePersistableUriPermission`**（拒绝不在系统里留痕），只置一次性 `notice`「「X」与已添加的「Y」重叠，请选择不重叠的文件夹」，复用全 App 的 Toast 轻提示口径。

**移除根目录。** 新增 `LocalMusicViewModel.removeRoot(treeUri)`：按 `treeUri` 从根目录表与内存索引里直接剔除（spec：不触发全量重扫），落盘索引，扫描在跑时取消旧任务并按新目录重跑。覆盖层按身份保留，重新添加同一目录后用户改过的信息仍在；移除后再选同一目录即恢复展示（指纹身份不变）。

不动系统里的持久化授权：正在播放的歌曲也是该树下的 content URI，`releasePersistableUriPermission` 会让它在 seek 时重开 fd 直接失败，与验收「正在播放的歌曲不受影响」相违；索引不再列出这棵树，不扫也就不会再读它。

**UI。** `AuthorizedFoldersDialog` 每行由「目录名」改成「目录名 + 移除」，并补一行说明「App 只扫描这些目录。移除后其中的歌曲会从列表消失，你改过的信息会保留。」与空列表文案；`AppNavigation` 把 `onRemove` 接到 `removeRoot(root.treeUri)`。

**评审收敛（两处状态一致性）。**

1. 移除后**无条件**落盘：原来把落盘交给「重扫」，但根目录被清空时 `startScan()` 直接 return、用户点取消或扫描失败也走不到写盘，磁盘会停在含该目录的旧快照，重启连歌一起捡回来。
2. 扫描提交只认**当前**根目录：`result.songs` 先按 `_roots.value` 过滤再合并覆盖层，落盘快照改成在写盘那一刻读 `_roots.value` / `_songs.value`（主线程两次读之间不会插入本 VM 的其他操作，快照必然同源）。原来的 `Snapshot(_roots.value, merged)` 会把「扫描开始时捕获的目录集扫出来的歌」与「落盘时的目录表」拼在一起，在扫描窗口内移除目录就会写出无主歌曲。

已知取舍：扫描完成提示的新增 / 移除数仍取自整次扫描（`ScanResult`），在「扫描窗口内移除目录」这一瞬态下可能与最终列表差一条；该路径紧接着会重扫一次，提示随即被下一次扫描的真实差值覆盖。
