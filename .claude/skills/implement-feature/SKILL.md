# Implement Feature Skill

在已有项目中实现新需求时，通过 **按需阅读分层文档** 快速定位上下文，再写代码。目标是：不读不相关的文档，不猜代码结构，用最少的阅读量获得足够的上下文。

---

## 第一步：理解需求，制定导航计划

先读清楚用户的需求，明确：
- 要实现什么功能？
- 涉及的是哪个层面（UI、API、数据库、业务逻辑、多模块交互）？
- 需要新增文件，还是修改现有代码？

**然后检查文档是否存在：**

```
项目根目录 PROJECT.md   ← 先检查这个
[模块]/PROJECT.md       ← 模块级
[模块]/doc/xx.md        ← 功能细节（按需读）
```

如果根目录 `PROJECT.md` 存在，继续第二步。  
如果不存在，跳到「**无文档时的回退策略**」。

---

## 第二步：从根目录 PROJECT.md 定位模块

读根目录 `PROJECT.md`（通常很短，快速扫描即可）。

你要从中得到：
1. **哪些模块与需求相关** — 根据「导航指引」和「模块一览」判断
2. **跨模块约定** — 如果需求涉及多个模块，注意 API 格式、认证方式等约定

**原则：只定位，不深挖。** 根目录文档的职责是告诉你去哪里，不是告诉你怎么写代码。

---

## 第三步：按需读取相关模块的 PROJECT.md

只读与需求相关的模块的 `[模块]/PROJECT.md`，不相关的模块跳过。

从每个模块的 PROJECT.md 中提取：
- **功能模块索引** — 有哪些 `doc/xx.md`，分别覆盖什么功能
- **目录结构** — 新代码应该放哪里
- **与其他模块的接口** — 如果需要跨模块调用，先看清楚接口
- **关键配置** — 环境变量、重要常量在哪里

根据索引，判断哪些 `doc/xx.md` 与需求直接相关。

---

## 第四步：按需读取相关功能细节文档

只读刚才判断为「直接相关」的 `doc/xx.md`。

每个 doc 文件开头都有 `> 何时阅读` 的提示 — 用它来二次确认是否需要读这个文件。

从 doc 文件中你需要关注：
- **关键文件列表** — 要改哪些文件
- **调用链 / 数据流** — 理解代码路径，知道在哪里插入新逻辑
- **关键接口/类型** — 新代码要遵循的接口约定
- **注意事项** — 避免踩坑

**不要把「可能有用」的 doc 也读进来。** 按需读取的意思是：只有当你判断「如果不读这个文档，我很可能写错代码」时，才读它。

---

## 第五步：读取必要的源码文件

有了文档上下文后，定向读取代码文件。

只读以下这些：
- 需要修改的文件（文档里已经指出了）
- 密切相关的接口/类型定义文件
- 如果是添加新接口，读一个现有的类似接口作为参照

**不要全量扫描目录。** 文档已经帮你定位了，相信它。

---

## 第六步：实现

基于以上上下文，完成实现：

1. **新增/修改代码** — 遵循模块现有的代码风格、命名规范
2. **如果涉及多个模块**，逐模块推进，先改后端/服务层，再改前端/消费层
3. **如果需要新文件**，参考模块 PROJECT.md 中的目录结构决定放哪里
4. **完成后简要说明**做了什么改动、影响了哪些文件

---

## 无文档时的回退策略

如果项目没有 `PROJECT.md`（`project-docs` skill 还没跑过），不要盲目猜测，按以下顺序操作：

1. **快速探索项目结构** — 列出顶层目录，识别子模块
2. **定位最相关的子模块** — 根据需求描述判断应该去哪里
3. **读入口文件和路由/目录结构** — 快速建立代码地图
4. **找相似功能参照** — 找一个已实现的类似功能，模仿其代码结构

完成后，可以顺带提示用户：「建议运行 `project-docs` skill 生成文档，下次实现需求时可以更快定位代码。」

---

## 按需读取的判断原则

这个 skill 的核心是**不读不必要的文档**。以下是判断标准：

| 情况 | 要读 | 不用读 |
|------|------|--------|
| 需求涉及「音乐播放」功能 | `doc/player.md` | `doc/download.md`、`doc/auth.md` |
| 需求涉及多个模块 | 所有相关模块的 PROJECT.md | 无关模块 |
| 新增 API 接口 | 已有类似 API 的路由和控制器文件 | 前端代码（除非同步修改） |
| 修改数据库字段 | 数据库 migration 文档、model 文件 | UI 组件代码 |

**经验法则：** 读完一个文档后，如果你能说出「我知道需要改 X 文件的 Y 部分了」，就不需要再读更多文档了。

---

## 文档和代码不一致时

项目文档不一定总是最新的。如果你在阅读时发现文档描述和实际代码不符，以**代码为准**。同时可以告诉用户：「发现文档中 X 的描述与代码不符，实际代码是 Y，建议更新文档。」
