# Project Docs Skill

生成一套 AI 友好的层级化项目文档，让未来的 AI 能按需只阅读相关文档，快速定位代码。

## 文档体系设计目标

文档不是写给人看的 README，而是给 **AI 导航地图**：
- AI 要修改某功能时，最多读 2 个文件就能知道所有相关的代码位置
- 每层文档都有明确的「什么时候读我」提示
- 避免重复信息，每层有自己的职责

---

## 第一步：探索项目结构

在写任何文档之前，先做侦查工作：

1. **列出顶层目录结构** — 找出有哪些子模块/子项目（通常是独立的目录，带自己的 `package.json`、`build.gradle`、`Cargo.toml` 等）
2. **对每个子模块**，快速扫描：
   - 入口文件（`main.ts`、`server.js`、`App.vue`、`MainActivity.kt` 等）
   - 目录结构（`src/`、`routes/`、`services/`、`components/` 等）
   - 依赖声明（`package.json`、`build.gradle` 等），了解技术栈
   - 现有 README（如果有，参考但不照搬）
3. **识别跨模块关系** — 哪些模块之间有 API 调用、共享类型、共用配置
4. **找出每个子模块的主要功能区域** — 这会决定要生成哪些 `doc/xx.md` 文件

探索要充分，宁可多读几个文件，确保理解清楚再写。功能描述要基于代码实证，不要凭猜测。

---

## 第二步：生成根目录 PROJECT.md

路径：`PROJECT.md`（项目根目录）

这是 AI 的入门地图 — 只需几分钟扫描就能了解项目全貌，知道要改什么功能应该去哪个子模块。

### 根目录 PROJECT.md 结构

```markdown
# [项目名称]

> **这是 AI 导航入口**。读完此文件你会知道项目由哪些模块组成、各模块做什么、以及要修改某功能时应该去哪里。

## 项目概述

[1-2 句话说明项目是做什么的]

## 整体架构

[简要描述各模块如何协作 — 数据流向、谁调用谁]

## 模块一览

| 模块 | 目录 | 技术栈 | 职责 |
|------|------|--------|------|
| [模块名] | `[目录]/` | [技术] | [一句话职责] |
| ... | ... | ... | ... |

## 导航指引

根据要修改的内容，直接跳转：

- **[功能A]相关改动** → 阅读 [`[模块]/PROJECT.md`]([模块]/PROJECT.md)
- **[功能B]相关改动** → 阅读 [`[模块]/PROJECT.md`]([模块]/PROJECT.md)
- ...

## 跨模块约定

[如果有跨模块的共同约定，记在这里：API 格式、认证方式、环境变量等]
```

## 第三步：为每个子模块生成 PROJECT.md

路径：`[子模块目录]/PROJECT.md`

AI 要在某个子模块里工作时，先读这个文件。读完应该知道：模块做什么、代码在哪里、功能细节文档的索引在哪里。

### 子模块 PROJECT.md 结构

```markdown
# [模块名]

> **何时阅读**：当你需要在此模块中添加、修改或调试功能时，首先阅读此文件。

## 模块职责

[2-3 句话说明此模块的核心作用，以及它在整个项目中扮演什么角色]

## 技术栈

- [框架/语言及版本]
- [主要依赖库及其用途]
- [构建工具/运行时]

## 目录结构

```
[根据实际项目内容生成，注释每个重要目录的作用]
src/
  api/          # HTTP 请求层，封装对后端的调用
  components/   # Vue/React 组件
  ...
```

## 功能模块索引

| 功能 | 文档 | 说明 |
|------|------|------|
| [功能名] | [`doc/[文件名].md`](doc/[文件名].md) | [一句话描述] |
| ... | ... | ... |

## 关键配置

[环境变量、配置文件、重要常量 — 告诉 AI 在哪里找配置]

## 与其他模块的接口

[此模块暴露了什么 API？依赖哪些外部服务？]

## 开发指南

[本地启动命令、构建命令、测试命令 — 简洁即可]
```

## 第四步：为每个子模块生成功能细节文档

路径：`[子模块目录]/doc/[功能名].md`

这是 AI 要修改具体代码前最后一步阅读的文档。读完应该知道：这个功能的关键文件是哪些、数据如何流动、有哪些重要的接口和注意事项。

### 如何划分 doc 文件

一个 `doc/xx.md` 应覆盖一个**内聚的功能区域**，而不是一个文件或一个类。好的划分标准：
- 修改这个功能时，通常需要同时改哪几个文件？ → 这些文件归为同一个 doc
- 这个 doc 大概 50-200 行 — 太短说明可以合并，太长说明需要拆分

**常见的 doc 划分示例**（仅供参考，根据实际项目决定）：
- `doc/player.md` — 播放控制逻辑
- `doc/api.md` — API 请求/响应层
- `doc/auth.md` — 认证/授权
- `doc/sync.md` — 数据同步
- `doc/download.md` — 下载功能

### 功能细节文档结构

```markdown
# [功能名]

> **何时阅读**：当你要修改[具体场景，如"播放队列逻辑"、"用户认证流程"、"文件下载功能"]时阅读此文件。

## 功能概述

[2-3 句话说明这个功能做什么，以及为什么这样设计]

## 关键文件

| 文件 | 职责 |
|------|------|
| `[相对路径]` | [这个文件在功能中扮演什么角色] |
| ... | ... |

## 数据流 / 调用链

[描述数据如何流动，或关键代码路径。可以用步骤列表或伪代码]

1. 用户触发 [操作]
2. [组件/函数] 调用 [API/方法]
3. [服务] 处理并返回 [结果]
4. [状态] 更新，UI 响应

## 关键接口 / 类型

[列出重要的函数签名、接口类型、事件格式等]

## 注意事项 / 已知问题

[坑、限制、非显而易见的设计决策 — 这对 AI 非常有价值]
```

## 写作原则

### 信息密度 > 篇幅

好文档不是长文档。每一句话都要有价值：
- **不要写**：「这个文件很重要，包含了很多功能」
- **要写**：「`usePlayer.ts` 管理播放状态(当前歌曲/队列/播放进度)，是播放功能的唯一状态源」

### 文件引用要精确

所有文件路径都用相对于该 doc 文件的路径（或相对于模块根目录），并用代码格式：
- 好：`src/services/musicService.js` 
- 差：「在 services 目录下」

### 「何时阅读」要具体

每个 doc 文件开头的 `> 何时阅读` 应该列出具体的修改场景，而不是泛泛的描述：
- 好：「当你要修改播放队列逻辑、切歌行为、播放进度保存时」
- 差：「当你要了解播放功能时」

### 不写没法验证的话

功能描述应基于代码实际内容，不要写凭想象的描述。如果某段代码的用途不确定，去读相关文件确认后再写。

### AI 导航的层次感

文档层次：
1. `PROJECT.md`（根）→ 知道去哪个模块
2. `[模块]/PROJECT.md` → 知道这个模块的功能分区和索引
3. `[模块]/doc/xx.md` → 知道具体代码在哪、如何运作

每层只负责自己层级的信息，不重复下层内容。

---

## 用户确认节点

如果项目结构复杂或有歧义，在以下情况向用户确认：
- 不确定某模块的主要职责时
- 功能 doc 文件的划分不够确定时（提出方案让用户选）
- 需要决定需要多细粒度的文档时

其他情况下，大胆推进，先生成，用户可以之后提出修改意见。
