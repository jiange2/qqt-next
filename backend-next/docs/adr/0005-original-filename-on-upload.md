# 媒体上传保留原名：冲突时追加递增后缀

上传到 OSS 的对象 key 不再随机生成，一律使用用户上传的原文件名（仅剥离路径分隔符与控制字符）；仅当同名 key 已存在时依次追加 `_2`、`_3` 后缀。DB 中存量 key（`时间戳_随机hex` 形态）不迁移，两种命名形态长期并存——新上传一律走原名规则。

动机：原名可读（管理员在 OSS 控制台和链接里能直接认出文件），且编辑歌曲界面需要向管理员展示音频 URL，随机名毫无辨识度。

## Considered Options

- **维持随机改名（时间戳/随机前缀）**：被拒。链接不可读，与本上下文"key 与 URL 分离、链接常驻展示"的方向冲突。
- **原名 + 随机前缀（图片旧规则）**：被拒。半可读半随机，比纯随机多不了多少辨识度，仍需查重。
- **完全原名、冲突时直接覆盖**：被拒。同名不同内容会被静默顶掉，且与本上下文"不删除/不覆盖旧对象"的孤儿保留策略矛盾。
- **URL 编码位置**：key 存原名原文不编码；所有 URL 生成点（遗留协议门面、管理面板展示）统一对文件名部分 `encodeURIComponent`。存库语义不变（媒体 Key 永不含域名与编码形态）。

## Consequences

- 中文、空格、`&`、`#` 等字符合法存在于 key 中；一切消费方必须走编码后的 URL，禁止手拼未编码链接。
- 服务端新增 OSS 查重能力（`doesObjectExist` / head），逐次探测 `_2` `_3` 直到可用。
- 不处理并发同名上传（两个管理员同时传同名文件）：管理后台单人使用，接受竞态风险。
- 编辑/替换时旧对象仍不删除（沿用 ADR 0004 的孤儿文件策略）；同 key 覆盖场景因冲突后缀规则天然不存在。
